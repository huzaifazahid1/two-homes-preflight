## Phase 1

| # | Decision | Reason |
| --- | --- | --- |
| 1.1 | `src/lib/env.ts` (server, `server-only`) and `src/lib/public-env.ts` (client) are two files instead of one. | If the server schema lived in a client-importable file, secret variable names would end up in the browser bundle (SE-1). |
| 1.2 | The agreement step (Phase 2) can be passed only when `NODE_ENV !== "production"` or `DEMO_MODE=true`, with "coming in this build" copy. | 1.3 | The family shell (owner only, no co-parent) is created when the profile step completes. `POST /api/family` is create-or-update and sets the co-parent's name and email. | Phase 2 agreement upload (step 2) needs a `familyId` before the family step (step 3). |
| 1.4 | `GET /api/paypal/connect/start` returns `{ url }` JSON and sets the state cookie; the page then navigates to PayPal. | Errors (401/403/400) can be shown inline instead of on a raw JSON page after a redirect. Same behaviour otherwise. |
| 1.5 | `DELETE /api/auth/session` has auth `none`: it always clears the cookie and revokes refresh tokens only if the session is still valid. | A user with an expired session must still be able to sign out cleanly (AU-6). |
| 1.6 | Cookie names: `thp_session` (5 days), `thp_link` (30 min), `thp_pp_state` (10 min). All httpOnly, SameSite=Lax, Secure when `APP_URL` is https. | Section F naming was open. |
| 1.7 | `CANCEL_EXPENSE` is allowed from NONE, RECEIPT_SUBMITTED, RECEIPT_ISSUE, READY, AWAITING_PAYMENT, PAYMENT_FAILED. Not from EXTERNAL_PAYMENT_REPORTED or DISPUTED. | "Any non-terminal before PAID": once a payment was reported or disputed, cancelling would hide that record. |
| 1.8 | No-op rule: an event whose target equals the current state is recorded as a `note` events row and not applied. Webhook-replayable events (`CAPTURE_COMPLETED`, `PAYOUT_*`) are also no-ops in later states. Every other disallowed pair is 409. | Section E.6.4 "already happened is recorded as noop". Late webhooks must not 409. |
| 1.9 | A derived expiry persisted by the next write gets its own events row stamped with `expiresAt`, and version increases by 2. | Invariant 11 (every state change has one events row) and correct timeline order. |
| 1.10 | Integration tests mock PayPal and Resend with a small local HTTP stub (`tests/helpers/stub-server.ts`) pointed to by `PAYPAL_API_BASE` / `RESEND_BASE_URL`, not MSW. `msw` stays installed for later unit tests. | MSW's Node interceptors stall the Admin SDK's gRPC (HTTP/2) channel to the Firestore emulator; Firestore REST mode needs real credentials. |
| 1.11 | The Playwright `phone` project uses the iPhone 13 profile on Chromium. | Only Chromium is installed; WebKit would be an extra download on a memory-limited machine. Viewport, touch and mobile UA are kept. |
| 1.12 | E2E runs `scripts/e2e-server.mjs`: `.env.test` in the process env (wins over `.env.local`), `E2E=true`, `DEMO_MODE=true`, build to `.next-e2e`, start on port 3100. `env.ts` refuses emulator variables in production unless `E2E=true`. | Section N.1 asks for `next build && next start` with emulators and outbox. Port 3100 avoids clashing with `npm run dev`. |
| 1.13 | `.env.test` has test-only dummy values (secrets, Firebase web config, PayPal ids). | `env.ts` validates them; they are not real secrets. |
| 1.14 | Added `POST /api/notifications/read` (own notifications only). | Clients cannot write Firestore, and the bell needs to clear unread items. |
| 1.15 | A second `POST /api/family/invite` while an invite is active is 409; `POST /api/family/invite/resend` is the explicit action that revokes and replaces. Invite sends are limited to 10/hour/user. | Prevents accidental double emails; LK-9 semantics stay explicit. |
| 1.16 | OTP codes are single use (cleared on success); the 5th wrong code clears the code and sets a 15-minute lock (423). A new code resets attempts. | Section F.3. 423 chosen over 429 for the lock so the UI can tell it apart from the send limit. |
| 1.17 | Changing the co-parent's email after an invite was sent revokes the active invite and resets the status to `not_sent`. After acceptance it is refused (409). | The old link would otherwise send codes to the old address. |
| 1.18 | The "invite accepted" notification is in-app only (`email.status = skipped`). | No email template for it in Section H.3. |
| 1.19 | Every `/app` page calls `requireOnboarded()` itself, not only the layout. `getMe()` calls `connection()` first. | Layouts and pages render in parallel, so a page cannot rely on the layout's redirect. Firebase session verification reads the clock, which is not allowed in a runtime prerender. |
| 1.20 | The Admin Firestore instance is cached on `globalThis`. | Next bundles route handlers and pages separately; `settings()` can only be called once per shared instance. |
| 1.21 | Status metadata (`VERDICT_META`, `INVITE_STATUS`) lives in `status-meta.ts` without `"use client"`. | Plain objects exported from a client module are client references in Server Components. |
| 1.22 | The type scale (`t-h1`, `t-amount`, ...) is defined with Tailwind `@utility`. | Allows responsive variants such as `sm:t-display`. |
| 1.23 | Sign-out, 401 redirects and `permission-denied` use `window.location.assign` (full reload). | Drops all client state and Firestore listeners after auth changes. Lint rule disabled on those lines with the reason. |
| 1.24 | `src/components/ui/drawer.tsx` durations lowered from 450 ms to 300 ms; `button.tsx` transitions list properties instead of `transition-all`. | Motion cap (P.9) and the web interface guidelines review. |
| 1.25 | Log in with PayPal authorize URL: `https://www.sandbox.paypal.com/connect?flowEntry=static&...`; userinfo `GET /v1/identity/oauth2/userinfo?schema=paypalv1.1`, parsed tolerantly (`payer_id`, `emails[]`/`email`, `verified_account` as boolean or string). Field names are logged once in development. | [Confirm] items 4 and 5: must be verified in the sandbox by the owner. |

## Phase 2

| # | Decision | Reason |
| --- | --- | --- |
| 2.1 | `Rule` gained optional fields: `childNames` (child-specific clause as written, matched by first name when `childIds` is absent), `supportingQuotes` (a value such as a receipt deadline taken from another clause, with its own verified quote), `issues` (why a rule needs a human) and `source` (`ai`, `demo`, `manual`). `RuleVersionDoc` gained `extraction`, `confirmedBy/At`, `supersededAt`, `updatedAt`; `AgreementDoc` gained `draftRuleVersionId`. | Children are added after the agreement step, so names cannot be ids at extraction time. A deadline clause is usually separate from the share clause; it still needs its own quote. Additive only. |
| 2.2 | Review issues: `quote_not_found`, `shares_invalid`, `shares_non_numeric`, `value_not_in_quote`, `conflict` block Confirm (rule is NEEDS_REVIEW); `quote_other_page`, `quote_fuzzy`, `vague_terms` are warnings. | A.6.2 "every value must trace to a verified quote". |
| 2.3 | Value tracing (SE-5): an AI percentage, dollar threshold or day count must appear in its quote (digits, common number words, "equally"/"half" for 50%). A parent's edit is trusted and keeps the AI values in `editedFrom`. | Prompt injection can make the model output a value, but not put that value in the document's real sentence. |
| 2.4 | Identical rules (same category, child scope and values) are merged; the copy with the best quote match is kept. Different values for the same category and scope are a conflict on both. | The fixture repeats clause 6.1 on page 6 on purpose; a repeated clause is not a conflict (AG-7 covers real conflicts). |
| 2.5 | `owedPct` is the share the non-buying parent owes, as in the data model. The extraction schema asks for both `payingParentPct` and `otherParentPct` and flags sums other than 100 (AG-6). Dollar amounts come back from Gemini as strings and are parsed with `parseDollarsToCents` (no floats). | Rule 8 (no floats for money). |
| 2.6 | An approval clause without an amount is stored as `{ operator: "gte", thresholdCents: 0 }` (always needs approval). | Fails safe: more approval, never less. |
| 2.7 | Extraction runs count only when they produce a draft (AI or demo mode). Free = 3 runs per family in total across uploads; manual entry never counts. A new extraction deletes the previous unactivated DRAFT of that agreement. | A Gemini outage should not use up the user's plan. Drafts that were never active have no expenses pinned to them. |
| 2.8 | Free plan: a second agreement upload or a second activation (amendment) is 402 while a version is ACTIVE. | A.6.5 "1 agreement" on Free; amendments are Family. |
| 2.9 | Manual rule entry: `POST /api/rule-versions/:id/rules` and `POST /api/agreements/:id/extract` with `{ "mode": "manual" }` (empty draft). Manual rules still need a quote found in the text. | AG-8 "manual rule entry offered"; nothing becomes a rule without a quote. |
| 2.10 | Gemini: `temperature 0`, `responseJsonSchema`, explicit `AbortSignal.timeout` (default 90 s, `GEMINI_TIMEOUT_MS`), SDK retries off, exactly one retry by us. `GEMINI_BASE_URL` (tests only) points the SDK at the local stub server. | The SDK's `httpOptions.timeout` was not enforced in tests. Same stub approach as decision 1.10. |
| 2.11 | Demo mode uses the recorded fixture output only when `DEMO_MODE=true`, the live call failed, and at least 80% of the cached quotes are found in the uploaded text. Its page numbers are taken from where the quote was found. The draft is labelled "Demo mode: cached extraction". | Never applies to any other document. |
| 2.12 | Pasted text pages: form feeds or marker lines (`--- Page 2 ---`, `Page 2 of 6`); otherwise ~4,000-character sections. Scanned PDF = under 40 letters per page on average; refused with `details.reason = "scanned"` so the UI switches to paste (ON-6). | |
| 2.13 | Calendar dates (planned/purchase) are stored at 12:00 UTC of that day and shown in UTC as a date. | A date without a time shows the same day in every time zone the app supports. |
| 2.14 | Expense creation writes the initial approval state from `initialApprovalState()` with one `expense.created` events row. Later approval changes go through `transition()`: an edit that needs `AMOUNT_RAISED` or `VERDICT_REQUIRES_APPROVAL` is written inside that transition (via `extraWrites`) so verdict and approval never disagree; the edit row is stamped 1 ms before the transition row. | Rule 7; deterministic timeline order. |
| 2.15 | Once approval is REQUIRED it stays REQUIRED when an edit lowers the amount (no table row goes back to NOT_REQUIRED). Edits are refused while a request is open, after a receipt, and after cancel. Edits re-check against the expense's pinned rule version. | E.6.1 has no such row; changing it is an owner decision. |
| 2.16 | Duplicate check (PF-7) uses equality on familyId + childId + amountCents (no new index) and compares normalised descriptions within 24 hours in memory. | Avoids a composite index. |
| 2.17 | Co-parent answers: `POST /api/links/:token/rules-ack` saves answers while the invite link is usable (before acceptance). Accepting also saves them. A changed answer re-checks expenses pinned to that version (AG-12) with a `verdict.recomputed` events row. | After acceptance the invite link is used, so invariant 8 makes it 410. |
| 2.18 | `src/lib/quote-verify.ts`, `src/lib/rules-review.ts` and `src/lib/rules-engine.ts` are pure and imported by client components (source highlight, issue text). | They import nothing server-only; one implementation for both sides. |
| 2.19 | UI: native `<select>` for child and category; shadcn `empty`, `spinner`, `kbd` added (no new npm packages). The quick add result never sets a child or amount the note does not contain (server check). | P.9 forms; PF-10 "unspecified fields empty". |
| 2.20 | `GEMINI_API_KEY` is blanked in `scripts/e2e-server.mjs`, so E2E uses the demo-mode cache deterministically. | E2E must not depend on a live AI. |
| 2.21 | Gemini calls set a thinking level (extraction LOW, quick add MINIMAL) on Gemini 3+ models and the equivalent token budget on 2.x models, which reject `thinkingLevel`. One retry waits 2 s after a 503/429. | On 2026-11-09 `gemini-3.8-flash` timed out (504 at 88 s) or returned 503 "high demand" on every call, also at temperature 1; `gemini-2.5-flash` passed the three-run check in about 10 s per run. The model is set with `GEMINI_MODEL`. |

## Phase 3

| # | Decision | Reason |
| --- | --- | --- |
| 3.1 | Cloudinary requests are signed with the SDK's own helpers (`api_sign_request`, `private_download_url`) and sent with `fetch` to `CLOUDINARY_API_BASE` (default `https://api.cloudinary.com`), with a hard timeout (`CLOUDINARY_TIMEOUT_MS`, 30 s). Not `upload_stream`. | The SDK picks http/https once at import time, so tests could not point it at the local stub, and it has no per-request timeout (RC-5). Same private upload parameters as Section I.2; no behaviour change. |
| 3.2 | Receipts are read by Gemini from the bytes already in memory at upload, not by downloading them again through a fresh URL (I.2 step 8). | Same file, one less network round trip and one less failure point. |
| 3.3 | Approval link: `linkTokens.resourcePath = approvals/{expenseId}_{n}`, same expiry instant as `approval.expiresAt`. `n` comes from `approval.currentRequestId`; `approvals/{id}` is created with `create()`. | One request per doc; concurrent requests fail on the existing id. |
| 3.4 | A second decision on a used approval link is 409 `STATE_CONFLICT` with `details.alreadyDecided` (AP-6), and `GET /api/links/:token` keeps showing the decision read-only. Expired and revoked approval links are 410; other action endpoints are 410 for used tokens (invariant 8). | AP-6 asks for 409 on the second decision; the phase edge cases ask for a read-only page after a decision. |
| 3.5 | The plain token is never stored, so every email that needs a link carries a new one. Approval: a resend or the 3-day reminder revokes the old link ("use the most recent email"). | 3.6 | Open request + `POST /approval-request` = a fresh link for the same request (3 per expense per day), not a new request. | "Create/resend" in the endpoint table; there is no REQUESTED to REQUESTED row. |
| 3.7 | Confirming a receipt re-runs the rules engine with the receipt total, date and submission time (A.6.1 steps 4 to 6) and stores that verdict. Shares use min(receipt total, approved). If the receipt now needs approval (threshold crossed or late), approval goes NOT_REQUIRED to REQUIRED through `transition()`. `expense.amountCents` keeps the planned amount. | The verdict stays the engine's; the receipt is the evidence. |
| 3.8 | Match issues OVER_APPROVED, MERCHANT_MISMATCH and POSSIBLE_DUPLICATE can be accepted by the parent (`acknowledge`), which resolves RECEIPT_ISSUE. BEFORE_APPROVAL and LATE need the other parent: an approval decided knowing it was bought (`approvals.purchasedBeforeApproval`) clears BEFORE_APPROVAL; an approval decided after the receipt was submitted clears LATE. | 3.9 | Same calendar day as the approval is not "before approval" (UTC days). | Receipts carry a date, not a time. |
| 3.10 | A new receipt uploaded in RECEIPT_ISSUE replaces the current one (kept with `replacedBy` as evidence) with a `receipt.replaced` note; the state changes on confirm. | E.6.2 has no RECEIPT_ISSUE upload row. |
| 3.11 | Free plan AI receipt reads (10/month) are counted in `usage/{familyId}_{yyyymm}.aiReceiptScans` only when Gemini is configured and called. | A missing key is a real error state (manual entry), not plan usage. |
| 3.12 | Disputes: the opening message plus at most 2 answers, taking turns. "agree" accepts the other parent's latest proposal (or the original amount). The second answer without agreement moves to UNRESOLVED. Earlier answers are timeline notes. | A.5.4 "up to 2 rounds of responses". |
| 3.13 | New notification types `external_payment_rejected` and `dispute_update` (with emails), additive to Section H.3. | The payer must hear about a rejected report and dispute answers; guests have no other channel. |
| 3.14 | Outstanding = AWAITING_PAYMENT, PAYMENT_FAILED, EXTERNAL_PAYMENT_REPORTED (CL-6). DISPUTED is listed but not in the totals. Overdue totals use `dueAt < now`. | Totals count what is owed; a disputed amount is not agreed. |
| 3.15 | The manual reminder gap counts from the last manual reminder only. After a skipped day the daily job sends only the latest applicable automatic reminder; an earlier one is never sent late. | "No duplicates, nothing missed" without a due-soon email after the due date. |
| 3.16 | Listeners only detect changes (expense `version`, or the list's ids + versions) and call `router.refresh()`; data is always re-read on the server. Paused listeners refetch on focus and `online`. | E.8: totals never from listener data. |

## Phase 4

| # | Decision | Reason |
| --- | --- | --- |
| 4.1 | The Server SDK gets its access token from our cached token in `paypal/http.ts` (`oAuthTokenProvider`), and its request URLs are rewritten to `PAYPAL_API_BASE` only when that is not the sandbox host (tests). | The SDK has no base-URL option; with our token provider the SDK never fetches tokens itself, so a test cannot authenticate against the real PayPal. One token for SDK and REST calls. |
| 4.2 | Payouts send `PayPal-Request-Id: payout-{sender_batch_id}` and, after a definitive 4xx rejection (e.g. `INSUFFICIENT_FUNDS`, which creates no batch), `payout-{sender_batch_id}-{n}`. The `sender_batch_id` itself never changes within an attempt. | A retry after a timeout must replay the original answer; a retry after a rejection must not replay the cached error. Double-payout protection stays with `sender_batch_id` (G.4). Found by PY-14. |
| 4.3 | After `INSTRUMENT_DECLINED` the next capture of the same order uses `capture-{orderId}-{n}` (count stored on the payment attempt). | Same reason: the restarted PayPal flow is a new try; the first key would replay the decline. |
| 4.4 | The `CAPTURE_COMPLETED` entitlement guard is satisfied when the capture belongs to an order this app created (orders are only created while entitled, 402 otherwise). | A plan that lapses between checkout and capture must not strand money already taken; SB-6 "payouts still sent". |
| 4.5 | Order attempt number = stored attempts + 1. Concurrent clicks compute the same number, so `PayPal-Request-Id` returns one order; the attempt is appended once by order id. | No lock document needed; G.8 key. |
| 4.6 | Insufficient platform balance: the claim stays `PAID`, the attempt keeps its `sender_batch_id` with `lastError`, an `payout.insufficient_funds` error log is the admin alert, and reconcile (button, job) retries. | G.4 step 7, PY-14. |
| 4.7 | A payout status for any batch other than the current attempt's is recorded as noop (stale). | A late FAILED for attempt 1 must not undo a successful retry (PY-13). |
| 4.8 | Webhook: bad or missing signature 400; PayPal verification unreachable or no `PAYPAL_WEBHOOK_ID` 500 (PayPal retries). Neither processes anything. | L.1 step 2 without losing events during a PayPal outage. |
| 4.9 | PayPal's subscription status `APPROVED` is stored as `APPROVAL_PENDING` (not entitled). `paidThrough` = `next_billing_time` and never moves backwards; `trialEndsAt` is set while the trial cycle runs. `families.plan.tier` is display only and follows entitlement on every sync. | E.2 has five statuses; PayPal drops `next_billing_time` on cancel (SB-3). |
| 4.10 | Fee line = ceil(uncovered x `FEE_PERCENT_BPS`/10000) + `FEE_FIXED_CENTS`, only when part of the claim is above this month's covered volume. Covered volume counts `owedCents` at capture, per UTC month (`usage/{familyId}_{yyyymm}`). | G.2; [Confirm 2] constants still to be read from a real sandbox capture. |
| 4.11 | PayPal error codes: `PAYPAL_DECLINED` 409 (with `details.restart`), `PAYPAL_DUPLICATE` 409, `PAYPAL_VALIDATION` 502, `PAYPAL_AUTH` 502. PayPal names and issues are logged with `debug_id`, never returned. New env `PAYPAL_TIMEOUT_MS` (default 30 s per attempt). | G.10, P.2. |
| 4.12 | Disconnecting PayPal is blocked (409) while a payout to that parent is `PAYOUT_PROCESSING` or `PAYOUT_UNCLAIMED`. Connecting sends payouts that were waiting in `PAID`. | PC-5, PC-6. |
| 4.13 | The daily job reconciles claims in `PAID`, `PAYOUT_PROCESSING`, `PAYOUT_UNCLAIMED` not updated for 10 minutes (filter in memory, no new index). The expense page re-reads a processing payout from PayPal when it was last checked over 60 s ago. | G.9, G.4 step 5. |
| 4.14 | AG Grid theme reads our CSS variables, so the light/dark switch re-themes the grid with one theme object. | K.2 asks for dark params; CSS variables give the same result without a second theme. |
| 4.15 | Demo seed (`/api/dev/seed`, `npm run seed`) drives the real route handlers in-process with a real session (custom token exchanged at Identity Toolkit). Reset deletes only families marked `demo: true` and users on `demo.twohomes.test`. | Every seeded state change takes the guarded path (rule 7); reset cannot touch real data. |
